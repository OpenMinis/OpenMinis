## 1. LONG-1 数据库迁移 O(N²)

`MIGRATION_20_21` 原来是逐行相关子查询：

```sql
UPDATE messages SET sort_order = (
  SELECT COUNT(*) - 1 FROM messages prior
  WHERE prior.session_id = messages.session_id AND (...)
)
```

每个 session 的每条消息扫一遍该 session → O(N²)。SQLite 窗口函数在项目支持的低版本 Android 上不可用，因此改为：

- 一个事务内按 `session_id, created_at, id` 排序读出 id；
- 复用一个 prepared `UPDATE messages SET sort_order=? WHERE id=?` 逐行编号；
- 最后建唯一索引。

O(N) 条语句、单事务，排序语义与旧 SQL、`MessageSortOrderMigrationTest` 完全一致。官方 instrumentation 迁移测试仍覆盖 `a→0, b→1, z→2` 与唯一索引。

## 2. LONG-2 搜索全表扫描 + N+1

### 2.1 用 compact preview 代替 parts_json

`messages.preview` 是 MIGRATION_18_19 / `updateMessageBody` 维护的紧凑投影：≤2 KB 的行是全量 parts JSON，更大的行是 ≤2 KB 的文本摘录。搜索改为：

```sql
WHERE s.title LIKE :pattern
   OR COALESCE(m.preview, m.parts_json) LIKE :pattern
ORDER BY s.updated_at DESC
LIMIT 200
```

- 不再为每个消息读取 5 MB 级 `parts_json`；
- `COALESCE` 只兜底迁移前没有 preview 的旧行；
- `LIMIT 200` 给最坏情况一个上界。

**为什么不是 FTS5**：内置 `unicode61` 不能命中中文子串（`会话` 在 `这是一个会话` 里不是独立 token），而中文子串正是本应用的主搜索场景。FTS4/5 需要自定义分词器，收益不抵复杂度。这里的取舍是"前 2 KB 可搜 + 有界扫描"，并记录在 DAO KDoc。

### 2.2 批量 snippet，去掉 N+1

新增 `ChatSearchDao`：

- `firstSnippetPerSession(sessionIds, query, radius, windowChars)` 一次查询返回每个 session 的首条命中（SQLite `GROUP BY` + `MIN(sort_order)` 的 bare-column 规则）；
- `SessionListViewModel.buildContentHits` 从"每个结果一次 `findFirstMessageSnippet`"改为一次批量查询；
- 搜索 SQL 从 914 行的 `ChatDao` 拆到独立文件，`ChatDao` 同时降回 887 行。

## 3. LONG-3 ResidentWindow 候选切点重复扫描

原 `byteCut` 对每个候选切点调用 `isLegalBoundary`，后者从该点扫到结尾 → O(N²)。

改为一次右到左预处理 `legalBoundaries(history)`：

- 结果（ToolResult）只能匹配它**左边**的 use，因此从右往左扫描时先进入 `pendingResults`；
- 遇到 use 先消费等待中的 result；消费不到则是未匹配 use，只有落在"最后一条 assistant 消息"里才允许；
- 每条消息边界记录 `pendingResults.isEmpty() && badUses == 0`；
- `byteCut` / `countCut` 之后只做 O(1) 的边界查询。

现有 `ResidentWindowTest` 的 13 条语义测试全部保留并通过（工具对、split round、裸 result、多 MB ToolUse 等）。

## 4. LONG-4 流式 overlay 全量重建

`mergeStreamingOverlay` 原来每 tick 对整条消息列表 `map`，为每个元素分配/调用 lambda。现改为惰性列表：

- `StreamingOverlayMessages : AbstractList<ChatMessage>`，只对 `streaming[m.id]` 命中的行 `copy()` 一次并缓存；
- 冻结行按引用返回，空 streaming 直接返回原列表。

同一批次里 `splitRounds` 也补上了 `fromIndex`：live build 只从"包含 `fromIndex - 1` 的 round"开始 fold，冻结 prefix 的 round 不再每 tick 重建。效果是：

- 多轮会话：每 tick 只 fold 当前 round；
- 单个超长 round（一条 user 后面几千条 assistant）：仍要 fold 这一轮，这是 round 语义本身的下界。

测试 `ChatFlatItemsSplitTest` 钉住"split build 的行是 full build 的严格后缀"以及"fromIndex 在末尾时不会出现更早 round 的行"。

## 7. UX-1 重组隔离

`ChatScreen` 仍是单个 7,579 行 composable，但消息区和输入区已经各自成为一个 **Compose restart scope**：

- 新增 `ChatRecompositionScopes.kt`：`ChatMessagesScope` / `ChatComposerScope`（带 `ColumnScope` receiver，保住 `Modifier.weight`/`align`）；
- 既有内联代码不移动，只在外面包一层 composable lambda；
- 消息区/输入区里的状态读取现在记在各自的 restart group 上：击键只重组输入区，滚动/消息行变化只重组消息区；
- 顺带删掉文件尾部十几行过时的 "moved verbatim" 注释。

**没有做物理文件拆分**：把 4,000 行消息区/2,000 行输入区搬进独立文件，需要同时搬走几十个局部变量、回调与 `remember`，风险远高于收益；重组隔离已经拿到性能收益，物理拆分留作可选的后续重构。

仍未消除的宽订阅：`messages`、`isStreaming` 等仍在 ChatScreen 顶层被 effect key / 弹层读取，这些是"消息条数/turn 边界"级别的变化，不是每 token；要彻底消除需要把弹层也包进 scope。

拆分方案（后续可选）：

- 物理 `ChatMessagesPane`：只订阅 `uiMessages` / `flatItems` / 滚动状态；
- 物理 `ChatComposerPane`：只订阅 `inputText` / attachments / 语音状态；
- `ChatOverlays`：审批、错误、compact、tool detail 各自订阅；
- 顶层 ChatScreen 只保留导航与 session 生命周期。
